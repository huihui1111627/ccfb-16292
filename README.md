# PawnRouter：收当消息条件分发中间件

用 Go 标准库实现的连锁典当行收当消息订阅、快速匹配、多级订阅合并与拓扑动态调整仿真。内置中文监控页面，无外部依赖、无需数据库或前端构建。

## 一键运行

```bash
# 仓库根目录直接启动；完整规模：固定种子 20261126，246,400 条生成订阅、2,400,000 条消息
go run .
# 或：go run ./cmd/server
# 打开 http://localhost:8088

# 快速冒烟：12 家门店、3 个区域、1,620 条订阅、20,000 条消息
go run . -scale small
```

常用参数：

```bash
go run ./cmd/server -addr :18088
go run ./cmd/server -scale small -messages 2000   # 临时覆盖消息数
```

## 正确性核对

核对器不复用候选索引和路由合并逻辑，而是重新生成同种子消息，按消息时刻的活跃订阅，对每家门店的每条订阅直接执行合取条件判断，再与仿真记录的投递位掩码逐位比较。

```bash
# 全量核对：240k 初始订阅 + 6.4k 动态新增/删除、240 万消息、64 门店
go run ./cmd/verify -scale full

# 快速小规模端到端核对
go run ./cmd/verify -scale small

# 输出各级订阅表大小、当前/已结束链路的流量和全量索引基准
go run ./cmd/stats -scale full
```

退出码为 `0` 表示没有漏投或多投；若非 `0`，会输出前若干条 `missing_delivery` / `extra_delivery`。

`go test ./...` 还包含：

- 开区间、闭区间边界；
- 多值属性任意值命中；
- 属性缺失时“不匹配/当作匹配”两种策略；
- 快速索引与逐条 oracle 的随机等价性；
- 合并过滤器对输入订阅的覆盖性；
- 小规模动态拓扑、动态增删下的端到端零差异；
- `go test -race ./...` 可检查并发回放。

## 页面能力

打开页面后可以看到：

1. **每台代理的两张表**
   - “收到”的订阅：门店原始订阅，或区域/HQ 从直接下级收到的上报；
   - “实际上报”的订阅：按当前允许超投比例合并后的过滤器，HQ 根节点额外展示同算法合并预览。
2. **合并前后表大小与压缩率**，可点开节点查看具体条件和 `SourceIDs` 血缘。
3. **每条链路的计数**
   - `Up`：发源门店向 HQ 上报的原始收当消息；
   - `Down`：父代理按下级上报表过滤后实际转发的消息；
   - `Necessary`：由子树真实送达结果反推的必要转发数；
   - 超投数和超投比例。
4. **最近每条消息的完整路径**：发源门店 → 上级 → HQ → 命中的区域/门店 → 精确投递，以及该消息在各级索引中的累计匹配耗时。
5. **匹配耗时直方图、P95 粗桶和 24 万订阅中央索引基准**。
6. **门店血缘追踪**：选择门店后，逐级展示它的原始条件、门店代理合并结果、区域收到的过滤器、区域再次合并结果以及 HQ 表中包含该血缘的条目。
7. **允许超投比例滑块**：按样本消息流中的额外命中比例估计合并代价；调整后所有代理订阅表立即重算。
8. **运行中加入/退出代理**：
   - 页面可添加 `RDxxxx` 区域代理，也可让区域代理退出；
   - 区域退出时，其直接下级原子改挂到父代理，订阅表随之重算；
   - 仿真过程中还会自动执行区域加入、门店迁移、空区域退出、带门店区域退出和 `R4` 故障式退出重挂。
9. **在线抽样直判核对**按钮，默认核对前 20,000 条消息。

## 条件模型

每条订阅是若干 `Clause` 的合取：

- 数值：`=`、`>`、`>=`、`<`、`<=`、`between`；
- 区间端点分别保存是否闭区间。消息值恰好等于边界时，只有对应端点为闭区间才命中；
- 字符串：`=`、`in`、前缀 `prefix`、包含 `contains`；
- 多值属性：消息中的一个属性可以有多个字符串/数值，任意值满足条件即该 Clause 命中；
- 缺失属性：订阅级 `missing_as_match` 决定消息缺少该属性时该条件放行还是整条不匹配。属性存在但值不满足仍为不匹配。

典型生成条件包括：

```text
category = "名表"
brand prefix "Role"
appraisal ∈ [20000, 100000]

category = "黄金"
gold_weight > 20
appraisal ∈ [10000, 80000]
```

## 快速匹配索引

`internal/pawn/matcher.go` 是只读候选索引：

1. 为每条订阅选择一个最有选择性的 Clause 作为 anchor：
   - 高基数品牌/型号字符串优先；
   - 窄数值区间优先于宽单侧区间；
   - 品类等值选择性较低，作为兜底。
2. 不同 Clause 类型进入不同索引：
   - 字符串等值/IN：哈希倒排；
   - 前缀：登记订阅前缀，查询消息值的所有 rune 前缀；
   - 包含：使用 rune unigram/bigram/trigram 签名；
   - 数值区间：每属性一棵随机 Treap 区间树，子树维护最大右端点，查询复杂度通常为 `O(log n + k)`。
3. 品类 eq/IN 额外构建位图，对所有 anchor 候选先做合取预筛，避免大量跨品类候选进入完整判断。
4. 收集候选后执行完整 `Predicate.Matches`，因此索引只负责“不漏候选”，最终语义仍由直接判断保证。
5. `MissingAsMatch=true` 的订阅按 anchor 属性单独登记；消息缺少该属性时也会成为候选。

## 多级合并与零漏投不变量

树为：

```text
HQ
├── R1 ... R8
│   ├── S01 ... S08
...
```

合并器按条件结构和品类值分组，在组内按数值下界/字符串键排序并贪心合并相邻过滤器：

- 数值条件合并为覆盖双方的最小安全包络；只有两个输入都有某一侧边界时才保留该侧边界，否则输出无界，确保覆盖；
- 等值合并为 IN；
- 前缀合并为最长公共前缀；
- 包含合并为双方目标串的最长公共子串；
- 合并后的 `MissingAsMatch=true`，以覆盖任一方“缺失即匹配”的语义；
- 空前缀/空包含在索引中作为通配 anchor 处理。

每个输出过滤器都保存 `SourceIDs`。合并允许变宽、允许样本估计的超投，但必须覆盖所有来源输入。HQ/区域可以多转发，门店代理最终仍用该门店的原始订阅做精确判断，所以终端门店收到的消息集合与逐条直判完全一致。

滑块的 `tolerance` 定义为：

```text
样本中被合并过滤器额外命中的消息数 / 样本消息总数
```

真实全量链路超投比不依赖该估计，而由仿真中的 `Down - Necessary` 统计。

## 动态事件

固定种子会生成：

- 240,000 条初始订阅；
- 6,400 条贯穿消息流的新增订阅；
- 6,400 条初始订阅删除；
- 2,400,000 条消息；
- 24 个订阅增删批次，避免逐条变更导致重复全量合并；
- `R9`/`R10` 加入、门店迁移、`R4`/`R10`/`R9` 退出和下级重挂。

核对器使用 `AddSeq <= seq < DeleteSeq` 判断某条订阅在该消息序号上是否活跃。

## 代码结构

```text
internal/pawn/model.go       # 条件、消息、直接 oracle
internal/pawn/matcher.go     # 候选索引、品类位图、池化去重
internal/pawn/interval.go    # Treap 区间索引
internal/pawn/merge.go       # 安全覆盖合并、样本超投估计
internal/pawn/generator.go   # 固定种子订阅/消息/拓扑生成
internal/pawn/network.go     # 树、路由、链路计数、动态代理
internal/pawn/simulator.go   # 固定种子并行回放、基准
internal/pawn/verify.go      # 独立逐条直判核对
internal/pawn/stats.go       # 页面 DTO 和门店血缘
internal/web/                # 嵌入式 HTTP API、HTML/CSS/JS
cmd/server                   # 页面服务
cmd/verify                   # 命令行全量/抽样核对
cmd/stats                    # 命令行统计表大小与链路流量
```

## 说明：性能与规模取舍

- 消息匹配和路由是内存仿真，不启动真实 Kafka/RPC；专线流量由链路计数器表达。
- 240 万条消息的路径文本不全部常驻内存；页面保留最近 160 条路径环并展示最新 100 条，同时为全部消息保存投递位掩码和路径匹配耗时。
- 全量 oracle 会执行数千亿次轻量条件判断，因此 `cmd/verify -scale full` 会使用所有 CPU，预计需要十几到几十分钟，具体取决于机器。
